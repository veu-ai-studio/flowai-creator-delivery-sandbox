## All distinct objections (107 across all 3 sub-batches)
**01. [sub-batch-1 · Slot 1] Registry validation breaks system**

> §6.4 Risk #1 for Agent #26 identifies that validateRoster() enforces exactly 25 agents, but the spec requires adding a 26th row. This creates a deployment-blocking race condition where the registry validation must be updated before Agent #26 can be added, risking system-wide breakage if not sequenced correctly.

**02. [sub-batch-1 · Slot 1] Dual-authority pattern untested at scale**

> Agent #26 §1 introduces dual-authority [recommend_only, auto_write_internal, requires_human_gate] at the primary-agent layer, which §6.3 admits is the FIRST agent to ship this way. The BaseAgent.guard() implementation for this pattern has no production precedent, creating systemic risk for Orchestra auto-admission.

**03. [sub-batch-1 · Slot 1] PII scrubbing incomplete for feedback**

> Agent #10 §6.4 Risk #1 mentions scrubCredentials() extension per CA-10-E.2, but the spec doesn't define how 'customer self-identified names' heuristic works. The 'My name is...' pattern is trivially bypassed, leaving PII exposure in customer feedback streams that flow to multiple downstream agents.

**04. [sub-batch-1 · Slot 1] Rubric files unspecified security hole**

> Agent #8 §6.4 Risk #1 states rubric content is 'not yet ratified' and §6.1 requires creating 5 new rubric files, but there's no specification of how these rubrics are loaded or validated. Dynamic rubric loading without signature verification creates code injection risk in the quality gate.

**05. [sub-batch-1 · Slot 2] Tamper-evidence limitations**

> Section 14.2 describes a tamper-evident log using a hash chain. However, it does not specify how the initial hash is secured or how the integrity of the hash chain is verified across distributed systems. This could lead to vulnerabilities if the initial hash is compromised or if there is no mechanism to verify the chain's integrity across different nodes.

**06. [sub-batch-1 · Slot 2] Agent #6 crawl decision ambiguity**

> In Section 6.4, there is ambiguity regarding how Agent #6 should handle partial ACE artifacts. The decision to supplement with its own crawl or accept partial input is not clearly defined, which could lead to inconsistent behavior and results.

**07. [sub-batch-1 · Slot 2] Rubric version drift risk**

> Section 6.4 of Agent #8 highlights the risk of rubric version drift, where changes to rubric files can alter scores for the same input, making historical comparisons difficult. This could undermine the reliability of trend analysis and governance decisions based on these scores.

**08. [sub-batch-1 · Slot 3] Lack of Rollback**

> The proposal does not provide a clear rollback strategy in case of failures or errors, which could lead to data inconsistencies and system instability. Specifically, §14.2 Tamper-evidence does not address how to handle hash chain breaks or corrupted logs.

**09. [sub-batch-1 · Slot 3] Insufficient Error Handling**

**10. [sub-batch-1 · Slot 3] Inadequate Security Controls**
